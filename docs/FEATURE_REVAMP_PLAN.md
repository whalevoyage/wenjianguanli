# FilePilot Lite 功能改版方案

> 定位变更：从「参赛型演示工具」转为**个人自用的本地文件管理台**。
> 本文只谈功能与架构改造，不含 UI 视觉改版（UI 另行处理）。

---

## 一、一句话目标

把现在这个「只能扫、只能查重、只能按类型搬家」的工具，升级成一个**能看清整块盘、能安全清理垃圾、能把文件跨盘搬家、而且整个过程看得见**的个人文件管理台。
除 Agent 页外，**全部功能纯本地跑，零 token、可断网**。

---

## 二、四条设计原则（先定原则，再定功能）

1. **本地优先** —— 除 Agent 外不联网、不调模型、不上传任何文件内容。
2. **危险操作一律先干跑** —— 任何删除/移动，先出清单给你看，确认后才执行。
3. **默认走回收站，不走永久删除** —— 物理删除只在显式勾选时可用，且二次确认。
4. **一切可回滚** —— 每个任务都留一份「操作账本」，支持一键回滚到操作前。

> 第 4 条是现有项目已有的好设计（`last_organization.json` 的撤销），本次要把它从「只支持最近一次整理」扩展成**通用任务账本**。

## 三、选项卡结构（10 个，分 4 组）

| 分组 | 选项卡 | 干什么 | 花 token |
|---|---|---|---|
| **总览** | 1. 首页 | 整机状态看板：各盘容量、可释放空间汇总、最近任务 | 否 |
| | 2. Agent 助手 | 用自然语言下命令 / 改项目自身 | **是（唯一）** |
| **分析** | 3. 空间地图 | 矩形树图可视化，钻取看谁在占空间 | 否 |
| | 4. 扫描分析 | 扫 C 盘 / D 盘 / 任意目录 / 单文件 | 否 |
| | 5. 重复文件 | 找内容完全相同的文件 | 否 |
| | 6. 垃圾文件 | 按规则找临时/缓存/残留/空目录 | 否 |
| **执行** | 7. 跨盘迁移 | 把一个盘的文件搬到另一个盘 | 否 |
| | 8. 任务中心 | 所有任务的流程图 + 实时进度 | 否 |
| **记录** | 9. 回收站 | 隔离区，误删可还原 | 否 |
| | 10. 操作日志 | 完整审计流水 | 否 |

### 关键点：目标选择器是**共享组件**，不是独立页

你说的「每个功能卡都能扫 C 盘 / D 盘 / 一个文件夹」——不要每页各写一遍，抽成一个组件 `TargetPicker`，放在每个功能卡的顶部：

```
[ 盘符: C:\ ▼ ]  [ 路径: D:\Workspace        ] [选择文件夹]
[ 范围: ○整盘  ○单目录  ○单文件 ]   [ 排除规则: 默认 12 项 ▼ ]
```

扫描、查重、找垃圾、迁移、清理**五个功能全部复用这一个组件**，保证口径一致。

## 四、现有代码复用盘点

好消息：**你要的功能，大半的地基已经在项目里了。**

| 新功能 | 可直接复用（现有代码） | 需要新写 |
|---|---|---|
| 扫描分析 | `backend/main.py::scan_path()` 的 `os.walk` + 分类统计 + 大文件收集 | 目录树输出、排除规则、进度上报、可中断 |
| 重复文件 | `duplicate_scan()` 的 `(size, sha256)` 分桶、`move_duplicates()` 的隔离区逻辑 | **先按 size 预分组**（现在对所有文件都算哈希，太慢）、分组可视化 |
| 垃圾文件 | `category_for()`、`format_size()`、`cleaner.py::remove_empty_dirs()`（现成的删空目录，只是没接上） | 规则引擎、安全分级、体量估算 |
| 跨盘迁移 | `organization_items()` 的路径规划、`/api/backup` 的 zip 逻辑（可复用为「打包搬运」模式） | **复制→校验→删源→建 junction** 四步流程、断点续跑、限速 |
| 回收站 | `move_duplicates()` 的 `.filepilot_recovery/` 隔离思路 | 走 Windows 回收站、还原、批量管理 |
| 任务中心 | `write_log()` / `read_logs()` 的日志账本 | **Job 任务模型 + SSE 进度推送** |
| 首页 | `Dashboard.vue` 的卡片体系、`getLogs()` | 各盘容量、可释放空间汇总 |
| Agent 助手 | `deepseek_client.py` 的空壳、`/api/ai/status` | 真接 DeepSeek、工具调用、**配方沉淀** |

**要扔掉/改掉的**：`/api/ai/scan-advice` 那个返回固定模板的假 AI（要么真做，要么删）。

## 五、最大的架构改动：从「同步阻塞」改成「任务化」

这是整个方案的技术核心，必须做，否则 C 盘扫描会直接把页面卡死。

**现状**：所有接口是同步的 —— 你点「扫描」，请求就一直挂着，直到扫完才返回。扫 C 盘可能几分钟，期间页面无进度、无法取消。

**改成**：

```
POST /api/jobs          提交任务 → 立刻返回 job_id
GET  /api/jobs          任务列表
GET  /api/jobs/{id}     任务详情
GET  /api/jobs/{id}/stream    SSE 实时推送进度   ← 流程可视化靠它
POST /api/jobs/{id}/cancel   中断任务
POST /api/jobs/{id}/rollback 回滚任务
```

任务模型：

```python
Job = {
  "id": "...",
  "type": "scan | duplicate | junk | migrate | clean",
  "target": "C:\\",
  "status": "pending | running | preview | done | failed | cancelled",
  "progress": {"phase": "正在读取目录", "current": 12340, "total": None, "percent": 42},
  "plan": [...],      # 干跑出来的待办清单
  "actions": [...],   # 实际执行的动作（回滚依据）
  "created_at": "...", "finished_at": "..."
}
```

**任务状态机（也就是你要的"流程可视化"）**：

```
扫描 ──▶ 分析 ──▶ 生成清单 ──▶ 等你确认 ──▶ 执行 ──▶ 校验 ──▶ 完成
  │                                        │
  └────────── 可中断 ─────────────────────┴──▶ 可回滚
```

任务中心页就是把每个任务画成一条这样的横向流程图，当前阶段高亮，实时进度条走。**SSE 用 FastAPI 原生 `StreamingResponse` 就能做，不用装 WebSocket 库。**

## 六、各选项卡详细设计

### 1. 首页 · 全局状态

**看什么**
- 各磁盘容量环：`C:` `D:` 已用/可用，红色高亮快满的盘
- 三个大数字：本次可释放空间（重复 + 垃圾合计）、已隔离文件数、待处理任务数
- 最近 5 个任务的状态条
- 一键入口：去清理 / 去迁移 / 去 Agent

**后端**：新增 `GET /api/overview` —— 聚合磁盘容量（`shutil.disk_usage`）+ 最近任务 + 回收站占用。

---

### 2. Agent 助手（唯一花 token 的页）

分两个能力，**必须分开设计**：

**能力 A：用大白话下命令（推荐先做）**
```
你：把 D 盘里 3 个月没动过的大文件挪到 E 盘
Agent：我理解为——扫描 D:\ 中修改时间 > 90 天且大小 > 100MB 的文件，
       预计 214 个 / 38.2GB，移动到 E:\Archive\。是否生成任务？
你：是
→ 生成一个本地工单，后续执行全程零 token
```
关键：**Agent 只负责"翻译意图 → 生成计划"，实际执行全走本地 API**。所以一次对话只调 1~2 次模型，token 消耗极低。

**能力 B：改项目自身**
- 改默认排除规则、改垃圾文件判定阈值、新增清理配方、调整卡片顺序等
- 通过受限的配置写入接口（不允许 Agent 改核心代码，只允许改 `config.json` / `recipes.json`）

**⭐ 配方沉淀机制（这个设计最省钱）**
Agent 把一次成功的意图，落成一条本地 `recipe`（JSON）：
```json
{ "name": "清 C 盘临时文件", "steps": [{"op": "junk_scan", "target": "C:\\", "rules": ["temp", "cache"]}, {"op": "clean", "to": "recycle_bin"}] }
```
以后同类需求**直接跑配方，零 token**。你用得越多，需要 Agent 的场景越少。

**token 控制硬约束**
- 只发**统计摘要**给模型，永不发文件内容/文件名全量列表
- 单次对话最多 2 轮调用，超出改为让用户确认计划
- 页面上实时显示「本次消耗 X tokens」

---

### 3. 空间地图 · 可视化

**做什么**：矩形树图（treemap）—— 每个色块 = 一个文件夹/文件，面积 = 占用空间。点一下钻进去看下层，面包屑导航回退。

**配色**：按文件类型分色（复用现有 8 类），大块上直接标名字和大小。

**技术选型**：这块建议引 **ECharts**（它的 treemap + 钻取是现成的，手写 SVG 实现钻取成本太高）。只在空间地图页按需加载，不影响其他页体积。

**后端**：新增 `GET /api/scan/tree?path=...&depth=3` —— 返回带大小的目录树（现在只返回扁平统计和大文件列表，层次信息是丢掉的，必须补）。

**性能红线**：C 盘全量递归会让磁盘 IO 打满。必须 --
- 默认只算 3 层，钻取时按需再展开
- 默认排除 `node_modules`、`.git`、`AppData` 深层、`$Recycle.Bin`
- 边扫边推送，不要等全部扫完才显示

---

### 4. 扫描分析

在现有基础上补三件事：
1. **可中断** + 实时进度（现在扫起来只能干等）
2. **排除规则**：默认 12 项，界面上可预览可改（现在完全没有排除，扫自己的项目会把 `node_modules` 全数进去）
3. **按时间维度**：增加"最近 30/90 天未修改"这类筛选（迁移功能要用）

---

### 5. 重复文件

**必须做的性能修复**：现在的实现是**对每个文件都算一遍 SHA256**。正确做法是三层过滤：
```
第 1 层：按文件大小分组 —— 大小唯一的直接淘汰（能干掉 95% 的文件）
第 2 层：只对同大小的文件算前 4KB 哈希
第 3 层：前 4KB 相同才算完整 SHA256
```
改完在几万文件的目录上大概是几十倍的速度差。

**可视化**：每组重复文件用一张"卡片 + 缩略预览"，标清楚「保留哪个 / 删哪个 / 能省多少」。

---

### 6. 垃圾文件（全新，本次重点）

**规则库横跨 3 个安全等级**：

| 等级 | 内容 | 默认行为 |
|---|---|---|
| 🟢 安全 | 系统临时文件、回收站残留、缩略图缓存、`.tmp/.bak` 残留、**空文件夹** | 默认勾选 |
| 🟡 确认 | 浏览器缓存、软件缓存、下载目录里的安装包（`.exe/.msi/.zip`）、日志文件 | 默认不勾选，需手动确认 |
| 🔴 谨慎 | 大于 1GB 的任何文件、`AppData` 下的数据目录、疑似个人文件 | 默认隐藏，需展开才显示 |

**关键：默认排除桌面。** 你明确说过桌面绝对不碰 —— 这条写进默认规则，且不允许在界面上轻易关闭。

**默认排除清单（不可选）**
```
Desktop、.workbuddy、FilePilotLite 自身目录、
C:\Windows、C:\Program Files*、C:\ProgramData、
$Recycle.Bin、System Volume Information
```

**复用**：`cleaner.py::remove_empty_dirs()` 已经写好了（只删空文件夹、不碰文件），直接接上就是「清除空目录」功能。

---

### 7. 跨盘迁移（全新，本次最有价值）

这个功能**我们之前手工做过一次**（C 盘搬到 D 盘），踩过的坑直接变成设计：

**四步法（每步都可中断、可续跑）**
```
① 复制    源 → 目标（跳过已存在的同名同大小文件）
② 校验    逐文件比对大小 + 哈希；任何一个不一致 → 立即停止，不动源文件
③ 删源    只有校验全部通过才删源
④ 建链接  可选：在源位置建目录联接（junction），让原程序仍能按老路径找到文件
```

**必须有的能力**
- **限速 / 串行**：一次只搬一个文件夹，加短暂 sleep，避免把磁盘 IO 打满（你之前就是被全量递归扫描卡死过机器）
- **预检空间**：目标盘剩余空间不足直接拒绝启动
- **跳过已存在**：支持「续跑」，中断后重来不会重复搬
- **迁移清单可导出**：搬家前先出一份 CSV，搬完拿它对账

**两种模式**
- 「移动」—— 复制+校验+删源（推荐，安全）
- 「打包搬运」—— 复用现有 `/api/backup` 的 zip 逻辑，打成包再搬（适合小文件海量场景）

---

### 8. 任务中心 · 流程可视化

每个任务一条横向流程图（就是第五节那个状态机），当前阶段高亮 + 进度条 + 当前正在处理的文件路径滚动显示。可以暂停、取消、查看清单、回滚。

**这一页是"让整个流程可视化"的主要落点。**

---

### 9. 回收站

取代现在的 `.filepilot_recovery/`，升级为：
- **走 Windows 回收站**（优先用 `send2trash`，或直接调 Shell API），这样即使不用本工具也能在系统回收站里找回来
- 保留现有「隔离区」作为备选模式（不进系统回收站，放在 `D:\_filepilot_trash\`）
- 列出隔离记录，支持「还原到原位」「彻底删除」

**注意**：现在代码里用的是 `shutil.move` 到恢复区 —— 这个逻辑本身没问题（可还原），但**没有回收站兜底**，且现在的「移动」接口没有记录足够信息做还原。

---

### 10. 操作日志

保留现有设计，但修掉三个已知失真：
- 页面写的「来源 activity.jsonl」→ 实际是 `logs.json`
- 页面写的「最多 50 条」→ 实际保留 500 条
- 备注列因为字段名对不上**永远显示"已记录"**

改成 Job 模型后，日志页直接读任务流水，信息会完整很多。

## 七、零 token 边界（你的硬要求）

| 功能 | 实现方式 | token |
|---|---|---|
| 首页 / 空间地图 / 扫描 / 查重 / 垃圾 / 迁移 / 任务 / 回收站 / 日志 | 纯 Python + 本地 API | **0** |
| Agent 对话 | 调 DeepSeek | 有 |
| Agent 配方执行 | 纯本地跑 recipe | **0** |

**断网验证**：关掉网卡，除 Agent 页外所有功能必须完全可用。这条当作验收标准。

## 八、安全设计（个人自用也不能省）

因为你是**要真删文件、真跨盘搬家的**，安全设计比功能更重要：

1. **三级安全开关**：只读模式（默认开？）/ 预览模式 / 执行模式
2. **危险目录黑名单**（不可绕过）：桌面、Windows、Program Files、ProgramData、系统回收站、本工具自身
3. **一切删除先进回收站**，物理删除需要显式勾选 + 输入确认词
4. **一切批量操作先生成清单**，清单可导出、可对账
5. **操作账本**：每个动作记录 `源 → 目标 + 时间 + 任务 id`，支持整体回滚
6. **空间预检**：迁移前检查目标盘容量
7. **扫描限流**：分片 + 可中断 + 深度限制，绝不一次性全量递归

## 九、改造优先级（建议分 4 期）

### 第 1 期 · 地基（必须先做，其他功能都依赖它）
- 任务模型 + SSE 进度推送（把同步接口改造成 Job）
- 目标选择器组件（盘符/目录/单文件 + 排除规则）
- 排除规则体系 + 安全黑名单
- 首页（磁盘容量 + 任务概览）

**做完这期，项目就算"活"了** —— 有进度、可中断、看得见。

### 第 2 期 · 三个分析功能
- 扫描分析（补排除规则、进度、时间维度）
- 重复文件（三层过滤提速 + 可视化）
- 垃圾文件（规则库 + 三级安全分级 + 空目录清理）

### 第 3 期 · 执行与可视化
- 空间地图（treemap + 钻取）
- 跨盘迁移（四步法 + 续跑 + 限速）
- 任务中心流程图
- 回收站

### 第 4 期 · Agent
- 真接 DeepSeek + 意图转计划
- 配方沉淀机制
- 受限的配置修改能力

**建议顺序不要变**：第 4 期的 Agent 必须建立在前三期之上 —— 否则 Agent 没有可调用的本地能力，只能继续返回假建议。

## 十、已知风险

| 风险 | 说明 | 对策 |
|---|---|---|
| C 盘全量扫描卡死机器 | 你之前就被这个坑过 | 分片 + 深度限制 + 排除规则 + 可中断 |
| 跨盘迁移中途断电 | 数据可能两头都缺 | 四步法：校验通过才删源；支持续跑对账 |
| treemap 渲染大目录卡顿 | 几万节点会卡 | 按层懒加载，只渲染当前层 |
| Agent 误操作 | 自然语言理解偏差可能生成错误计划 | Agent 只生成计划，真执行前**必须人工确认** |
| 磁盘空间读数不准 | 沙箱/缓存会导致读数偏差 | 以「目标盘剩余空间预检 + 执行后复查」为准 |

## 十一、需要你拍板的点

1. **回收站策略**：默认走 Windows 回收站，还是走工具自己的隔离区？（回收站更安全，但系统盘回收站也会占空间）
2. **空间地图是否允许引 ECharts**？（约 1MB，但 treemap 钻取手写成本很高）
3. **Agent 是否需要「改项目自身」的能力**？这块风险最高，建议先只做「读状态 + 下命令」，改配置放最后一期。
4. **第一期先做哪个**？我建议**先做任务模型 + 目标选择器 + 首页**，因为这是所有功能的地基。
